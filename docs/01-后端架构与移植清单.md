## 2. 项目级对象图：`ProjectContext`

旧实现用 Dagger `ProjectComponent`（`@ProjectSingleton`）。新实现**不使用 Spring 自定义 scope**，而是显式工厂：

```java
// wp-kernel
public final class ProjectContext implements AutoCloseable {
    ProjectId projectId;
    ProjectIndexes indexes;            // 全部索引实例（见 §3.2），含 RootIndex
    IndexUpdater indexUpdater;
    RevisionStore revisionStore;       // BinaryOWL
    RevisionManager revisionManager;
    HierarchyProviders hierarchies;    // class / object / data / annotation
    DictionaryManager dictionary;      // Lucene 短名字典 + 搜索
    RenderingManager rendering;
    EntityCrudKitHandlerCache crudKits;
    ProjectEventManager events;        // 带 EventTag 的事件桶
    ChangeManager changeManager;       // 实现 HasApplyChanges
    ReadWriteLock lock;                // 项目级读写锁
    Instant lastAccess;
    void close();                      // 关闭 Lucene writer、停止事件清理线程
}
```

- `ProjectContextFactory.create(ProjectId)`：按旧 `ProjectModule`（`<core>/inject/project/ProjectModule.java`，724 行）的 provider 顺序手写构造：目录 → `RevisionStore.load()` → 构造索引 → `IndexUpdater.buildIndexes()` → 层级 Provider → Lucene（若无索引目录则全量建） → `ChangeManager`。
  - 已实现（S1）：应用层协作者（项目详情、前缀、CRUD kit 设置、讨论、标签、关注、创建权限检查、搜索过滤器）通过 `kernel.project.ProjectPorts` 注入，共享线程池通过 `KernelThreadPools` 注入；`close()` 先等待项目读写锁，再按打开的逆序释放（事件清理任务 → Lucene searcher → writer → directory → 等待修订写盘完成），不关闭共享线程池。构造失败时已打开的资源同样释放。
- `ProjectRegistry`（Spring 单例，`wp-app`）：Caffeine `expireAfterAccess(webprotege.project.dormant-time)`，`removalListener` 调 `close()`；`get(projectId)` 加载时按 projectId 加锁，对应旧 `ProjectCache`。
  - 已实现（S3，`app.project`）：Caffeine 只负责判断项目何时空闲，哪个上下文处于打开状态由注册表自己记录，因为 Caffeine 的移除通知是异步的。打开和关闭都在该项目的锁内进行，旧上下文关闭后才打开新的（否则新上下文拿不到 Lucene 写锁）。到期由注册表自己的线程按时触发，并在该线程上关闭项目。另提供 `getIfLoaded`（读取时不算使用，对应旧 `getProjectEventManagerIfActive`）、`close(projectId)` 和 `closeAll()`。Bean 由 `ProjectRuntimeAutoConfiguration` 创建，只在存在 `ProjectPorts`（S4/S5）和 `DataDirectoryLayout` 两个 bean 时生效。
- 应用层服务通过 `ProjectRegistry.get(projectId)` 拿到 `ProjectContext`，再调用其中对象。索引接口依旧按类型取用：`ctx.indexes().get(ClassFrameAxiomsIndex.class)`。

### 3.4 并发与锁

- 每个 `ProjectContext` 一把 `ReentrantReadWriteLock`。读服务取读锁；`ChangeManager.applyChanges` 取 `changeProcessingLock`（串行化变更生成）后再取写锁，与旧实现一致。
- 修订落盘线程、事件清理线程、索引更新线程池：全部由 `wp-app` 的 `KernelExecutors` bean 提供，`ProjectContext.close()` 不关闭共享池。
  - 已实现（S3）：索引更新 10 个线程（同旧），修订落盘 4 个线程（每个项目自己保证写盘顺序），事件清理 1 个线程；线程数可用 `webprotege.kernel.index-update-threads` 和 `revision-write-threads` 配置。

权限检查：每个服务方法在入口调用 `accessManager.require(Subject.forUser(userId), ProjectResource.of(projectId), BuiltInAction.X)`，抛 `PermissionDeniedException`（→ 403）。写服务另外在 `ChangeManager` 外层调用 `require(EDIT_ONTOLOGY)` 与按实体类型的 `CREATE_*`（迁移自旧 `ChangeManager` 的检查）。
- 已实现（S5）：`app.access` 的 `AccessManager`（实现 `MongoAccessManager`，移植自旧 `AccessManagerImpl`）提供 `require(UserId|Subject, Resource, BuiltInAction)` 和 `requireSignedIn(UserId)`；`PermissionDeniedException` 继承 `app.error.WpException`（`code: PERMISSION_DENIED`，403）。约定：服务方法凡带 `caller` 参数，第一行就做检查；不带 `caller` 的方法只供认证、命令行和其他服务调用。按实体类型的 `CREATE_*` 检查是 `AccessChangePermissionChecker`（实现内核端口 `ChangePermissionChecker`，提示语沿用旧版），由 S6 组装 `ProjectPorts` 时接入。
- 与旧实现的差别：去掉了权限缓存。旧实现在内存里缓存"有权限"的结果，角色变化时只清掉其中一部分；现在 `wp-cli` 会从另一个进程修改角色分配，撤销的权限必须立即生效，而每次检查只是一次走 `(userName, projectId)` 唯一索引的查询。角色闭包仍按旧实现的方式计算（同样的哈希顺序和重复项），所以写出的 `RoleAssignments` 文档与旧版相同。

### 5.3 Mongo 文档与仓库（Spring Data MongoDB）

数据库名 `webprotege`（取自 `spring.data.mongodb.uri`）；集合名、`_id` 与字段名与旧版一致。旧数据里 Morphia 写入的 `className` 读取时忽略；新写入不产生 `_class`（`MappingMongoConverter` 设 `DefaultMongoTypeMapper(null)`）。

旧代码用三种方式写 Mongo，新实现（S4，`app.<feature>.persistence`）逐一对应：
- **Morphia 实体**（8 个集合）：Spring Data `@Document` record；嵌入的 OWL 实体由 `OwlEntityMongoCodec` 读写。
- **`objectMapper.convertValue(record, Document.class)`**（9 个集合）：照旧用与旧版配置相同的 Jackson `ObjectMapper` 转换（`JacksonDocumentMapper`），文档就是领域对象的 JSON，不再另写 `*Document` 类。这类数据里有 Jackson 自己的类型字段，例如 crud kit 后缀设置的 `"_class": "Uuid"`，所以不能交给 Spring Data 映射。
- **手写转换**（`Users`）和只做 upsert 的 `ProjectAccess`：`@Document` record。

下表字段以旧代码的实际输出为准（S4 用旧代码生成的样本核对过，修正了本节原先的 `avatarUrl`、`UserActivity.userId`、`UserApiKeys.userId`、`Forms.descriptor`、评论 `id` 等写法）。

## 6. 安全（`wp-api`）

| 关注点 | 设计 |
|---|---|
| 浏览器登录 | 前端 OIDC Authorization Code + PKCE（Keycloak client `webprotege-web`），携带 Bearer JWT 调 `/api/v1/*` |
| JWT → UserId | `preferred_username` claim；首次见到的用户写入 `Users`（realName 取 `name`，email 取 `email`） |
| 系统管理员 | JWT realm role 含 `webprotege.auth.admin-realm-role` → 请求上下文附加 `SYSTEM_ADMIN`（不落库） |
| API Key | `ApiKeyAuthenticationFilter`：`Authorization: ApiKey <key>` → SHA-256 → `UserApiKeys`；成功则构造 `UsernamePasswordAuthenticationToken(userId)`；与 JWT 并存，JWT 优先 |
| 本地兜底 | `webprotege.auth.local-login.enabled=true` 时启用 `/login` 表单（BCrypt，`Users.localPasswordHash` 新字段），仅供 dev 与首个管理员；不迁移旧 MD5 密码 |
| 授权 | 服务层 `AccessManager.require(...)`；控制器不做授权 |
| CSRF | 关闭（Bearer/ApiKey 无状态）；同站 Cookie 不用于认证 |
| `/download`、`/data/*` 兼容层 | 同一 Security 链；允许 `?apiKey=` 查询参数仅用于下载链接（可配置关闭） |

已实现（S5，`api.security`）：
- **一条链**：`SecurityConfiguration` 覆盖全部路径，无会话、无 CSRF、无请求缓存。免认证的只有 `/actuator/health`、`/actuator/info`、`/v3/api-docs`、错误页；其他请求都要认证，授权在服务层。401 与 403 的响应体是 Problem JSON（`code` 分别为 `UNAUTHENTICATED`、`PERMISSION_DENIED`），401 带 `WWW-Authenticate: Bearer`。Prometheus 用 API Key 抓取（`authorization: {type: ApiKey, credentials: …}`）。
- **JWT**：按令牌的签发方选择解码器（`JwtIssuerAuthenticationManagerResolver`）：Keycloak 的令牌用 Spring Boot 按 `issuer-uri` 建的解码器，并校验 `audiences: webprotege-api`；本地兜底登录的令牌用它自己的公钥。其他签发方的令牌一律无效。`UserJwtAuthenticationConverter` 取 `preferred_username`；没有该声明，或用户名会被旧 `UserId.isGuest()` 认作 guest（该方法判断的是 `"guest".endsWith(name)`），令牌按无效处理。
- **管理员 realm 角色**：令牌带上权限 `ROLE_SYSTEM_ADMIN`。`wp-app` 的端口 `ExternalRoles` 由 `SecurityContextExternalRoles` 实现：只对当前请求的用户、只在应用资源上加 `SystemAdmin`。它依赖请求线程的安全上下文，交给其他线程执行的工作看不到这个角色。
- **API Key**：`ApiKeyAuthenticationFilter` 排在 bearer 过滤器之后，已被 JWT 认证的请求不再处理，所以 JWT 优先。查不到的 Key 直接 401。认证结果像 bearer 令牌一样保存在请求属性里，异步响应也能用。`?apiKey=` 只对 `GET /download` 本身有效（`webprotege.auth.api-key.allow-query-parameter`）。生成和吊销 Key（`POST`、`DELETE /api/v1/me/api-keys`）只接受 bearer 令牌，泄露的 Key 不能给自己续出新的 Key。
- **本地兜底**：形式有调整。表单登录要靠会话 Cookie，与"无状态、不用 Cookie 认证"矛盾，所以改为 `POST /login`：接收表单字段 `username`、`password`，用 BCrypt 校验 `localPasswordHash`，成功后返回本服务签发的 RS256 bearer 令牌（`{access_token, token_type, expires_in}`，签发方 `urn:industrial-ontology:local-login`，有效期 `webprotege.auth.local-login.token-ttl`）。签名密钥在启动时生成、只在内存中，令牌只在本实例有效，重启后失效。未知用户和错误密码返回相同的 401 `BAD_CREDENTIALS`。同一用户名连续失败 5 次后锁定 15 分钟（429 `TOO_MANY_ATTEMPTS`）。凭证只从请求体读取，放在查询串里返回 400。认证服务内部出错时返回 503 `AUTHENTICATION_UNAVAILABLE`。
- **端点**：`GET /api/v1/me`，`GET/POST /api/v1/me/api-keys`，`DELETE /api/v1/me/api-keys/{apiKeyId}`，`GET/PUT /api/v1/admin/settings`，`GET /api/v1/admin/users?q=&limit=`（见 02 §2），控制器上有 springdoc 注解。`/admin/permissions/rebuild` 随 `rebuild-permissions` 在 S6 实现。

## 7. 可观测与运维

- Actuator：`health`（含 Mongo、数据目录可写检查）、`metrics`、`prometheus`。
  - 已实现：数据目录检查为 `DataDirectoryHealthIndicator`；Mongo 检查（S4）是 Spring Boot 的 `MongoHealthIndicator`，随 `wp-app` 引入的 Mongo starter 自动提供，组件名 `mongo`。

- 日志 MDC：`projectId`、`userId`、`traceId`。
- 优雅停机：`ProjectRegistry.closeAll()` 等待修订落盘线程完成。
  - 已实现（S3）：`server.shutdown: graceful` 先让进行中的请求完成；之后 Spring 按 bean 依赖先调 `closeAll()`，再关闭 `KernelExecutors`。顺序不能反：每个项目的写盘任务是串起来的，线程池先关闭会让后面的修订被拒绝、丢失。

## 8. `wp-cli`

| 命令 | 行为 |
|---|---|
| `create-admin --user <name> --email <e> [--password]` | 写 `Users` + `RoleAssignments(SYSTEM_ADMIN, projectId=null)`；`--password` 仅在本地兜底启用时有意义 |
| `generate-api-key --user <name> --purpose <p>` | 等同旧命令，输出一次明文 |
| `rebuild-permissions` | 重算 `RoleAssignments` 闭包 |
| `set-permissions --project <id> --user <name> --role CAN_VIEW\|CAN_COMMENT\|CAN_EDIT\|CAN_MANAGE` | 同旧 |
| `migrate-mongo` | §5.3 迁移脚本 |
| `reindex-lucene --project <id>\|--all` | 删除并重建 Lucene 索引 |

实现：Spring Boot `ApplicationRunner` + picocli，独立可执行 jar，复用 `wp-app`。
- 已实现（S4）：`WebProtegeCli`（非 Web 的 Spring Boot 应用）用 `CommandLineCliRunner` 执行 picocli 根命令 `wp-cli`，各命令是 `@Component` 的子命令（目前只有 `migrate-mongo`，后续命令在 `WebProtegeCommand` 的 `subcommands` 中登记）。数据库与服务器相同，取 `WP_MONGODB_URI`，也可写成 Spring Boot 参数 `--spring.data.mongodb.uri=…`：形如 `--a.b=c` 的参数交给 Spring Boot，不传给命令。退出码：0 成功，1 失败，2 参数错误，`migrate-mongo` 另有 3 表示执行完毕但列出了问题。`wp-cli` 关闭启动时的索引检查（`webprotege.mongo.ensure-indexes: false`），以保证 `--dry-run` 不改库。
- 已实现（S5）：`create-admin --user <name> --email <e> [--password]`，`--password` 不带值时交互输入、不回显，带值时可用于脚本。用户不存在就创建；已存在则保留姓名和旧字段，只改邮箱。邮箱属于其他用户时拒绝。`SystemAdmin` 加到该用户已有的应用角色上，不像旧 `SetupTools` 那样把其他应用角色替换掉。`generate-api-key --user <name> --purpose <p>` 用选项代替旧命令的交互输入，只输出一次明文；用户还没登录过也可以生成（供集成账号使用），这时会提示一句。参数不合法时两条命令都退出 2，并打印原因和用法。
